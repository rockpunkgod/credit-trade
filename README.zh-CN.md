# Credit Trade

[English](README.md)

Credit Trade 是一个本地沙箱，用于构建厂商中立的、经授权 API 推理服务按量买卖平台。供应方登记其声称控制的接口端点，平台识别模拟服务，购买方获得版本化报价；随后，系统对模拟推理调用进行计量，并将结果记入借贷平衡的复式账本。当前沙箱不会核验端点控制权或服务授权。

本仓库**不交易 API credits、个人订阅额度、促销余额或可转让储值**。

## 当前安全状态

| 能力 | 当前状态 |
|---|---|
| 供应方与购买方流程 | 仅限本地模拟沙箱 |
| 推理服务提供方 | 仅使用模拟端点；未启用任何真实厂商 |
| 购买方资金与供应方收益 | 仅为模拟账本分录；尚未实现提现，也没有真实资金流动 |
| 生产支付 | 不可用，且默认失败关闭 |
| 市场准入 | 所有未知或未经审查的组合均为 `PENDING_REVIEW` |
| GitHub Release | 尚未发布 |

未知的厂商、支付通道、供应方类型、市场或证据缺口均保持 `PENDING_REVIEW`。只有现行官方来源明确禁止的适用范围才会标记为 `PROHIBITED`；沙箱不会因为缺少信息就推定禁止。两种状态都不能解锁生产支付。

模拟流程只能作为技术测试证据，不能视为支付服务商沙箱验证、厂商授权、法律批准、市场运营资格或真实资金交易。

## 运行要求

- Node.js 24 或更高版本
- pnpm 11 或更高版本

当前内存版演示不需要 Docker、PostgreSQL、Redis、生产凭证或第三方账户。

不要将 API key、支付凭证、完整性/HMAC 密钥材料、身份文件、合同或法律意见放入本仓库。未来的集成只能接受经批准的秘密管理器引用或环境变量名称，不能把秘密值写入源代码或文档。

先确认当前终端可以使用以下两个命令：

```powershell
node --version
pnpm --version
```

在 Codex Desktop 中，随附的 Node 运行时起初可能不在终端的 `PATH` 中。如果无法识别 `node --version`，可仅为当前 PowerShell 会话添加该路径：

```powershell
$creditTradeNodeBin = Join-Path $env:USERPROFILE '.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin'
$env:Path = "$creditTradeNodeBin;$env:Path"
```

## 本地运行

当前沙箱没有第三方运行时依赖。启动 API：

```powershell
pnpm start
```

在另一个终端中运行完整模拟流程：

```powershell
pnpm demo
```

演示程序会自行启动临时本地 API 进程，因此不必预先运行 `pnpm start`。它会按以下顺序调用已经实现的 HTTP 接口：

1. 创建模拟供应方；
2. 登记并识别其模拟推理端点；
3. 创建沙箱购买方，并获取仅展示一次的 API key；
4. 创建不可变报价并计算最大预占金额；
5. 发起模拟推理请求，完成预占、按实际用量结算并释放剩余金额；
6. 查看最终用量和保持借贷平衡的账本。

所有调用都不会离开本机，演示输出也不会打印原始 API key、完整提示词或完整模型输出。

运行自动化测试：

```powershell
pnpm test
```

API 默认监听 `http://127.0.0.1:3000`。已经实现的准确接口契约见 [`docs/api/openapi.yaml`](docs/api/openapi.yaml)。

模拟数据使用 10% 平台费，并以整数最小货币单位记录每 token 价格。这些只是演示值，不是已批准的商业条款。

## 计费与计量

内部模块 `packages/core/src/billing` 将用量计量、精确计价和账本结算分离。版本化计量模式声明输入、输出、缓存读取、缓存写入、工具调用和请求六类维度。当前模拟流程只使用估算的输入/输出 token 和一次请求；尚不支持的缓存及工具维度会明确记录为零。

用量记录包含来源、最终状态、执行结果、模式版本和内容摘要，但不保存提示词或输出。计价策略会快照价格与费率版本，并支持“每一百万 token 若干最小货币单位”等精确有理费率。所有数量和金额继续使用十进制字符串与 `bigint`，不使用浮点数记账；舍入规则会明确记录，当前按每条用量记录执行。普通 SHA-256 内容摘要仍只是确定性内容标识，单独使用时不能证明真实性。

每份报价会在推理前绑定价格摘要以及计量/计费策略版本。预占、结算和释放分录会作为一个可回滚的内存批次提交；即使注入提交中断，系统也不会遗留冻结余额，并可安全重试。生产化之前仍需数据库事务与持久化唯一约束。

核心现已为内部模拟供应方/KYB fixture 记录、包含已存 API key 哈希的购买方记录、平台费率/报价有效期策略、厂商端点记录、按版本连接的供应价格、报价策略、用量、计价、币种级账本检查点和结算添加经过域分离的 `CT-HMAC-SHA256-V1` 完整性封印。供应方和购买方封印只认证沙箱记录及其内部归属，不证明真实 KYB、API key 持有权或授权。平台策略封印会绑定计费策略版本、平台费率和报价有效期，因此在新报价被合法封签之前，普通进程内状态改写会导致完整性验证失败；这不等于生产配置获批。作用域字段绑定沙箱环境、市场、币种、购买方、供应方、端点、报价和推理。每条供应价格流都有前驱链接和独立的本地链头；报价封印把选中的供应价格封印作为父项，随后形成“报价 → 用量 → 计价 → 结算”关系。结算还会认证 HMAC 请求码、已交付输出摘要、金额和当前推理的完整有序账本批次，并推进按币种隔离的内存结算链。

每个改变账本的分录批次还会为各受影响币种的完整分录历史和当前物化余额创建一个 HMAC 认证检查点。验证过程会从分录重新计算余额，按不受 locale 影响的顺序生成余额摘要，检查业务键索引和各检查点前缀，并拒绝伪造充值分录、形式上仍平衡的改写以及物化余额改写。严格的规范化验证会拒绝访问器、意外字段、稀疏数组和带附加属性的数组。它还要求供应方、购买方和报价的 Map 键精确一致，购买方/API key 哈希索引双向一致，幂等 Map 键精确一致，且每个已消费报价都精确对应一条推理、一条计费记录和一条幂等记录，同时要求报价的 `USED` 状态与这组记录覆盖关系一致。

不透明 HMAC 认证码会绑定环境、市场、购买方、报价、幂等键和提示词，而幂等记录不会保存明文请求指纹或提示词。重放时会验证该认证码，并从已认证的规范化推理/计费状态重建可信结果，而不是把缓存结果本身当成证据。端点登记、价格发布、购买方模拟入账、报价创建和推理都会先执行完整性预检，因此一旦发现历史篡改，新的计费变更会被熔断。购买方身份和 API key 哈希索引只会在初始入账分录/检查点创建成功后发布；在已测试的检查点签封失败中，不会遗留购买方、哈希索引、分录或检查点状态。状态、计费和账本读取也会先验证完整目录、账本和计费关系。完整性失败会默认拒绝，HTTP 只返回脱敏的服务端错误。公开 HTTP 响应字段不会增加封印、完整性 key ID 或密钥材料。

这是一种带认证的篡改检测，不是加密，也不是数字签名。当攻击方没有活动 HMAC 密钥且独立的内存价格/结算链头与检查点历史保持完整时，它可以检测记录改写；在价格链头保持完整时，还能检测删除最新本地价格版本。端点记录虽有封印，但没有独立外部锚定的端点集合链头，因此纯本地验证通常不能发现一个未被其他记录引用的端点被删除。这些控制不能证明估算用量真实，不能在密钥或进程失陷后阻止伪造，不能供第三方独立验证，也不能独立防止记录、索引、本地链头和检查点被协调回滚。默认沙箱会在进程启动时生成一个临时的 32 字节密钥；所有状态和密钥都会在重启时丢失，因此不能提供跨重启验证。生产环境仍需要职责分离的 KMS/HSM 密钥、持久化轮换和历史验证、事务型存储、外部锚定的目录/价格/结算链头与账本检查点、追加式/WORM 保留以及独立审计监控。

沙箱只接受系统内部生成的用量，购买方不能自行上报计费数量。当前 UTF-8 字节估算器只是确定性的技术测试逻辑，不是厂商权威 tokenizer、厂商账单或支付对账证据。模拟输出会先按照不可变报价上限截断，再进行计量，因此超出上限的输出既不会返回，也不会收费。

已经实现的计量/计价边界见 [`docs/adr/0003-sandbox-billing-metering-boundary.md`](docs/adr/0003-sandbox-billing-metering-boundary.md)，带认证的完整性设计及其限制见 [`docs/adr/0004-authenticated-metering-integrity.md`](docs/adr/0004-authenticated-metering-integrity.md)。

## 初版限制

- 所有状态都保存在内存中，进程停止后会丢失。
- 默认 HMAC 完整性密钥、价格/结算链头和账本检查点历史仅存在于当前进程；重启后，封印不能作为可独立验证的持久证据，且尚无供应方/端点库外部锚点。
- 只有 `mock://acme-ai` 和 `mock://contoso-ai` 可以执行模拟推理。
- 用量只是本地沙箱估算，不是厂商权威计量或账单对账。
- 其他格式有效的端点会以 `PENDING_REVIEW` 状态登记，但系统绝不会连接或路由到这些端点。
- 购买方在请求报价时需要指定供应方端点；尚未实现多供应方自动路由。
- 尚未实现流式响应、取消、持久化、RBAC/MFA、退款、拒付、供应方提现及支付服务商沙箱适配器。

## 生产锁

当前版本没有生产支付适配器或生产推理适配器。前端开关或普通环境变量都不能让本沙箱获得生产能力。未来每个市场都必须分别完成运营主体、支付、KYC/KYB、制裁筛查、税务、隐私、数据驻留、厂商授权、双人批准和限额真实试点证据审查，之后才能启用任何真实资金功能。

预期市场包括中国大陆、中国香港、新加坡、美国和欧盟，目前均未上线。美国尚未限定州，欧盟尚未限定成员国；请求或资金绝不能在不同市场间故障转移。

## 仓库结构

- `apps/api`：本地 HTTP 控制面与推理接口
- `packages/core`：内存沙箱领域核心、定价、计量和账本逻辑
- `packages/core/src/billing`：计量模式、用量记录、精确计价与带认证的完整性函数
- `scripts/demo.ts`：可执行的端到端模拟流程
- `docs/api/openapi.yaml`：已经实现的 HTTP 契约
- `docs/compliance`：合规证据元数据规则；机密证据保留在 Git 之外
- `docs/security`：安全假设与风险登记
- `docs/runbooks`：运维与恢复说明

当前生命周期状态见 [`docs/project-status.md`](docs/project-status.md)，精确的外部恢复条件见 [`docs/blockers.md`](docs/blockers.md)。
